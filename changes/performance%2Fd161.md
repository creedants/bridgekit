Deleting an account now asks Paddle to cancel a live subscription before the workspace and its subscription row go. Before, the delete removed only rows, and the `subscription` row cascaded away with the workspace while Paddle kept billing a subscription nobody could reach.

- `server/paddle.ts` adds `cancelSubscription`, which posts to `/subscriptions/{id}/cancel` with `{ effective_from: "next_billing_period" }` and turns an unreachable Paddle or a non-ok answer into `PaddleCancelError`. `server/workspace.ts` reads each sole workspace's subscription before any delete and cancels every row that is not already `canceled`, then marks it `canceled` so a retry of the same deletion sends no second request. Only after every sole workspace is settled does the organization delete run. A Paddle failure refuses the whole deletion with `SUBSCRIPTION_CANCEL_SENTENCE`, thrown as an `APIError` so better-call answers with that sentence and a 503.
- The period end is the decision, not an immediate cancel. The `case "canceled"` branch of `hasPro` in `server/paddle.ts` keeps Pro until `currentPeriodEnd`, and `assertCheckoutOpen` in `server/workspace.ts` treats that same row as subscribed until then, so cancelling immediately would forfeit time the customer already paid for.
- `server/auth.ts` still calls `deleteSoleWorkspaces(env.DB, user.id)` with no `PaddleAccount`. Passing the account in that one production call is the remaining step; the optional third argument keeps the current call compiling.
- `test/workspace.test.ts` covers a Paddle refusal and an unreachable Paddle leaving the organization and subscription rows in place with the sentence, an already-canceled row and a workspace with no row deleting without a request, and the existing deletion test passing a fake account. `test/paddle.test.ts` covers the request and the two `PaddleCancelError` answers.
- `privacy.html` says a workspace with a paid subscription is deleted only after its subscription is cancelled in Paddle.
