- Export Excel and loading an `.xlsx` file now share one Excel library loader in `src/app/exportExcel.ts`. When that chunk cannot load, both actions say `The Excel tools could not load. Check your internet connection and try again.` instead of the browser's `Failed to fetch dynamically imported module` text, and the same click works after the connection returns with no page reload and with the loaded data still on the page.
- Chromium keeps a failed dynamic import failed for its address for the life of the page. After a failed load, the next attempt imports a fresh copy of the chunk at `?retry=<stamp>`, an address the browser has not cached as failed, so the recovery works however the first attempt failed, including a connection that drops after bytes have arrived. The failed address is never fetched or imported again. A retry fetches the fresh address once to check that it answers as JavaScript and then imports that same address, which is not the preflight round 1 shipped, because round 1 checked the bare address and could not protect the import that followed it.
- `src/app/sheet.ts` takes the library from that loader, and the page's loader `excelTools` is its default, so no code outside the loader names the chunk's address. `src/app/db.ts` reads an `.xlsx` file through `firstSheetAsCsv`.
- The chunk-loading machinery that recovers a failed Results or DuckDB chunk moved from `src/app/db.ts` to `src/app/exportExcel.ts`, so both files can reach it. Its behaviour for those chunks is unchanged, including the stamped retry after a failed load.
- `test/excel-offline.test.ts` models the browser with the loader's own fresh-copy seam: the bare chunk address never recovers, and only a fresh copy under a stamped address does. It asserts the sentence and no download or file read on the first failed action, a workbook with a `Bridge` worksheet and the same three CSV lines on the next one, one fresh copy for later actions, and a lexical source scan finds one checked line containing the literal text `xceljs` after its comment/type-line filters. That line is the shared loader's dynamic `import("exceljs")` in `src/app/exportExcel.ts`. The scan rejects the exercised static and single-quoted imports, the `"\x65xceljs"` spelling, a `.mts` file, and the exercised same-line comment/type-statement cases. It allows whole-line type-only statements and a simple `type X = typeof import("exceljs")` alias. Other escaped spellings and runtime code skipped by its filters can bypass the scan.
- `scripts/smoke.mjs` blocks the Excel chunk in a production preview build, checks the sentence and no workbook, then checks a workbook and an `.xlsx` load in the same page, repeats the plain offline-then-online pair for both actions, and fails if the browser record holds no stamped retry.
- Only `src/app/exportExcel.ts`, `src/app/sheet.ts`, `src/app/db.ts`, `src/app/App.tsx`, `test/excel-offline.test.ts`, `scripts/smoke.mjs` and this file changed. `App.tsx` changed in round 1 only, where it took `lazyChunk` and the sentence type from their new home in `exportExcel.ts`.
