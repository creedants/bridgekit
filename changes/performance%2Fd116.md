- Export Excel and loading an `.xlsx` file now share one Excel library loader in `src/app/exportExcel.ts`. When that chunk cannot load, both actions say `The Excel tools could not load. Check your internet connection and try again.` instead of the browser's `Failed to fetch dynamically imported module` text, and the same click works after the connection returns with no page reload and no loss of the loaded data.
- The loader proves the chunk's own address answers before importing it, so an attempt made while that address cannot be fetched does not import it, and the other action's import of the same address still works once it loads. Chromium keeps a failed dynamic import failed for that address for the life of the page, and `src/app/sheet.ts` imports the same `exceljs` chunk by that address. The proof is one same-origin GET whose body is cancelled after its first read, on the first Excel action of a page.
- The chunk-loading machinery that recovers a failed Results or DuckDB chunk moved from `src/app/db.ts` to `src/app/exportExcel.ts`, so both files can reach it. Its behaviour for those chunks is unchanged, including the retry that suffixes the address after a failed load.
- `src/app/db.ts` reads an `.xlsx` file through `excelSheetAsCsv`, and `src/app/App.tsx` imports `lazyChunk` and the sentence type from their new home.
- `test/excel-offline.test.ts` drives both actions through a loader whose importer fails while offline and succeeds after reconnecting. It asserts the sentence offline, the workbook and the sheet contents after reconnecting, and that a new file under `src/app` does not import `exceljs` directly instead of using the shared loader.
- Only `src/app/exportExcel.ts`, `src/app/db.ts`, `src/app/App.tsx` and `test/excel-offline.test.ts` changed in code.
